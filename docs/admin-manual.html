1. About this manual

This manual documents the PRDF Admin Console as a SuperAdmin sees it — which is everything. It covers every screen, every tab, every control, and the rules behind them. Where a rule is enforced by the database rather than the interface, that is said explicitly, because those are the rules you cannot talk your way around.

1.1 What a SuperAdmin can do that others cannot

  • See every case regardless of who it is assigned to
  • Drive any status transition, overriding the role that normally owns that stage
  • Grant and remove roles, including Admin
  • Reset a user's multi-factor authenticators
  • Move money — disburse and record repayments
  • Read every report and the audit trail
The override is the dangerous part. A SuperAdmin can advance a case past a stage its owning role has not signed off. The system will let you; the audit trail will record that you did. Use the override for genuine operational recovery, not to save a colleague a phone call.

2. The system at a glance

PRDF runs two web applications against one API and one database.

PartAddressWho uses it
Admin Consolehttps://prdf-admin.vercel.appInternal and workflow staff
Client Portalhttps://prdf-lms.vercel.appApplicants holding the Client role
APIhttps://prdf-api.vercel.appBoth front ends
Database, auth, storageSupabase project prdfThe API

2.1 How a request is authorised

  1. You sign in against Supabase Auth, which issues a signed token.
  2. The console sends that token with every API call.
  3. The API verifies it, loads your roles from the database, and checks them against the action.
  4. Row-level security in the database checks again, independently.
Two gates, deliberately. The interface hides what you may not do, but the interface is not the control — the API is directly callable. Anything enforced only in the browser is advisory. This is why some rules below say "enforced by a database trigger": those hold even if someone calls the API directly.

2.2 Where documents live

Uploaded files go straight from the applicant's browser to a private storage bucket using a short-lived signed URL. The API never handles the file itself; it records that the document exists and validates its type and name. Files are only ever served back through signed links that expire.

2.3 Multi-tenancy

The platform is built to serve more than one lender. Branding, eligibility copy and domains come from a tenant configuration resolved from the hostname at page load. There is deliberately no default tenant — an unrecognised hostname shows an error rather than serving the wrong brand.

There are eight workflow roles, plus management and administrative roles, plus the client.

3.3 The rules that matter

  • Only Finance Officer, Admin and SuperAdmin may move money. Anyone else attempting to disburse or record a repayment is refused by the API.
  • Only a SuperAdmin may grant Admin.
  • The Client role cannot be assigned from the console at all — it is granted when someone registers in the portal. This is deliberate: a staff member must not be able to turn a colleague into a borrower.
  • A Client-only user is blocked from the console, and a user with no Client role is blocked from the portal.
  • Stage workers see only cases assigned to them. Management roles see everything.

4. Signing in and access control

Sign in with your PRDF email address and password. Your session persists across browser restarts and expires after a period of inactivity. Logout is at the top right of every screen.

4.2 Layout

The left sidebar holds the six destinations: Dashboard, Pipeline, Loans, Portfolio, Reports, User Access. The top bar shows who you are signed in as, an alerts bell, your Profile, and Logout. A breadcrumb above the page title shows where you are.

What you see depends on your roles. A Finance Officer does not see User Access; a stage worker sees a shorter Pipeline. This manual describes the SuperAdmin view, which is the complete one.

5. The application lifecycle

Every application moves through a fixed sequence of eleven stages. The rail at the top of each case shows where it is.

Draft → Submitted → Screening → Due Diligence → Evaluation → Approved
      → Board Approved → Contracting → Disbursed → In Repayment → Closed

Two branches leave the main line at almost any point:

  • Info Requested — more is needed from the applicant. Returns to Submitted or Screening once supplied.
  • Rejected — the application is declined. Available from every stage up to Contracting.

5.1 Who may advance what

From stageNextOwned by
DraftSubmittedThe applicant
SubmittedScreening, Info Requested, RejectedIntake Clerk
ScreeningDue Diligence, Info Requested, RejectedProgram Officer
Due DiligenceEvaluation, Info Requested, RejectedRisk Analyst
EvaluationApproved, RejectedReview Committee / Program Manager
ApprovedBoard Approved, RejectedBoard

DisbursedIn RepaymentFinance Officer
In RepaymentClosedFinance Officer
Illegal jumps are refused by the database, not just the interface. You cannot move a case from Submitted straight to Approved even by calling the API directly — a trigger rejects the write. The dropdown only ever offers the transitions that are actually legal from the current stage.

5.2 Two gates worth knowing

  • Submission requires every required document type to be present. Enforced by trigger.
  • Approval requires every required document to be Verified, not merely uploaded. Enforced by trigger. This is the single most common reason an approval is refused — see Section 9.

5.3 When the loan record is created

The loan is created when the case reaches Board Approved, in PendingDisbursement status. That is the moment the rate, days financed and fees are fixed — see Section 11.

7. Pipeline

Pipeline is the full case list. The filter chips are All open, Screening, Due Diligence, Evaluation, Info Requested, Approved, Contracting and SLA Breached. Cases past their service standard carry a red SLA breached · n days badge.

How a case is named. Every case reads {business name} {applicant's first name} {application date} — "Blue Harvest Aquaculture (Pty) Ltd Test 4 Sep 2026". The name is derived from the record, never stored, so it cannot drift from the client it describes, and the loan inherits it when the application is booked. Pipeline, the case file, My Loans and the applicant's own list therefore all call the same deal the same thing.

Before this, a case was labelled with whatever free text the applicant typed into "tell us more about how you'll use the funds". Older screenshots and any notes written before 28 September 2026 may still refer to cases that way.

9.2 Verifying

Approval is blocked until every required document is Verified. Uploaded is not enough — a database trigger checks for at least one Verified document of each required type when a case moves to Approved, and refuses the transition otherwise. If an approval is rejected and the reason is not obvious, this is almost always why.

9.3 Rejecting a document

Reject marks a document as not accepted. The applicant sees the rejected badge against that document in their portal and can upload a replacement in its place — the slot stays open until they do. Rejecting does not change the case status and does not, on its own, notify them; see 21.2 for what they actually see.

9.4 Requesting a document

Rejecting handles a document that arrived and was not good enough. Request document handles the other case — something that never arrived at all, or something that is on no checklist.

The dialog has four fields:

FieldWhat it does
Document type One of the ten checklist types, or Other (not on this list). A type with a request already open is shown as "— already requested" so you do not stack two asks for the same thing.
Document name Appears only for Other, and is required there. This is the name the applicant sees, so write it as they would recognise it — "Signed lease agreement", not "lease".
Details Optional, shown to the applicant verbatim underneath the document name. Where to find it, or what it has to show.
File type PDF, Word (.doc or .docx), or any accepted type. This sets what their upload box will accept, so choosing PDF for something only issued as a Word file will block them.
Be specific, in the Details field. "Bank statements unclear — please upload the full three months including August" gets a useful answer. "More info needed" produces another round trip and another week. The Details field is the one the applicant actually reads.

What happens next

  • The applicant gets an in-app notification and an upload slot on their status page — this is the whole point of the feature, and 21.1 shows it from their side.
  • The Documents tab tells you what you are waiting for: "Waiting on the applicant for 1 requested document."
  • When they upload against the request it closes itself and links to the document they sent, which then goes through the normal Verify / Reject flow in 9.2 and 9.3.
  • If they later delete that document — which they can only do while the application is still a draft — the request reopens rather than sitting there claiming to be satisfied.
Requesting a document does not move the case. It stays in whatever stage it was in. This is deliberate — a reviewer can ask for a payslip without parking the whole application in Info Requested, and an ask the applicant cannot see never gets answered. Use Request info in the left rail when you do want the case to stop and the status to say so.

Withdrawing a request

A request you raised in error is cancelled, not deleted. It stays on the case as part of its history, and the audit trail records both CreateDocumentRequest and CancelDocumentRequest against your name. There is no way to erase one, by design.

10. Advancing a case

10.1 The sequence

  1. Assign the case to whoever owns the next stage, and click Save assignment.
  2. Choose the next status from Change status.
  3. Write a status note saying what you checked and why you are moving it.
  4. Click Update status.
Write the note every time. It is optional and it is the single most valuable thing in the case file. The History tab becomes the audit trail of the decision — and when a case is queried months later, or reviewed externally, notes are the only record of why. "Approved at R750 000 over 12 months at 17.00% (Moderate). All required documents verified." takes ten seconds and answers every future question.

11. Pricing tab and the risk grade

The Pricing tab does two different things, and the difference matters.

  • The quote is a calculator. It computes and shows; it stores nothing.
  • The risk grade decision is stored on the application, and is what the loan is actually booked at.

11.1 The inputs

InputNotes
Principal (R)Pre-filled from the requested amount
Days financedPre-filled from the term (365 ÷ 12 × months). Check it — it drives the interest
Risk gradeLow, Moderate, High or Worst. Sets the margin over Prime
Days lateFor modelling a penalty. Leave at 0 for a normal quote

11.2 Saving the grade

Choose the grade, click Calculate quote to check the numbers, then Save grade as …. The grade is stored against the application and audit-logged.

Grade the case before it reaches Board Approved. The loan is created at that point, at whatever grade is stored. If nothing is stored, it falls back to the legacy flat product rate and the case is booked at the wrong price. The warning on an ungraded case exists for exactly this reason.
The grade locks once the loan exists. After Board Approved the panel reads "This case is booked at … The grade is now fixed — a booked loan keeps the rate it was priced on," and the save button is disabled. A booked rate is a snapshot; re-grading afterwards would disagree with what the client was told.

12. The credit model in full

Four income streams, one of which only applies when a client pays late. Capital is never revenue.

ComponentFormulaWhen
InterestPrincipal × annual rate ÷ 365 × days financedOver the term
Initiation feeFlat R1 000Once-off
Management feePrincipal × 3%Once-off
Penalty(Principal + interest) × 2% × (days late ÷ 30)Only when late

12.1 The rate

Annual rate = Prime + the risk grade's margin. Prime is currently 10.5%.

GradeMarginAnnual rate
Low5.0%15.5%
Moderate6.5%17.0%
High8.5%19.0%
Worst10.5%21.0%

12.2 Bullet, not amortising

Interest is simple, charged daily on the full principal, and frozen at maturity. There is no declining balance. The client makes one payment at maturity covering capital plus interest, so the repayment schedule has a single row.

12.3 Fees are deducted from the advance

The once-off fees are taken off the money paid out, not added to the schedule. This is why the model defines total due to funder as principal + interest and excludes fees.

12.4 The worked example

ItemAmountHow
PrincipalR750 000,00Requested
Annual rate17.00%Prime 10.5% + Moderate 6.5%
Days financed36512 months × 365 ÷ 12
InterestR127 500,00750 000 × 17% ÷ 365 × 365
Initiation feeR1 000,00Flat
Management feeR22 500,00750 000 × 3%

12.5 Late payment

There is no grace period; penalty accrues from the first day late, linearly, and never compounds on earlier penalties. For the example above:

Days latePenaltyTotal revenue
30R17 550,00R168 550,00
60R35 100,00R186 100,00

Rounding is up to the cent. This can differ from the client's spreadsheet by a cent on some totals. It is a deliberate configuration, not a defect.

13. Money tab — disbursement

Once a case reaches Contracting the left rail reads "Ready for payout" and offers Go to Money →.

FigureMeaning
OutstandingCapital still owed
PrincipalThe amount advanced
Scheduled DueTotal of the schedule — capital plus interest
Interest RateThe booked annual rate, with the grade beneath it
TermMonths, with days financed beneath
StatusPendingDisbursement, Disbursed, InRepayment or Closed
Initiation / Management feeThe once-off fees, snapshotted at booking

Pay out the net advance, not the principal. For a R750 000 loan the client receives R726 500; the R23 500 of fees is retained. The field is labelled "pay out this amount" for that reason, and the console will not let you disburse more than it.

13.1 Disbursing

  1. Enter the Amount — the net advance.
  2. Enter a Reference — use the bank's payment reference so the two records reconcile.
  3. Click Disburse.

Disbursing does four things at once: records the payment, sets the loan to Disbursed, moves the application to Disbursed, and generates the repayment schedule. The applicant sees all of it immediately in their portal — Section 22.2 shows exactly what appears on their side, including the balance question this reliably produces.

Disbursement is not reversible from the console. There is no undo. Check the amount and the reference before clicking.

14. Money tab — repayments

14.1 The repayment schedule

For a credit-model loan the schedule is a single row: the full principal plus interest, due on the maturity date. Each row shows its number, due date, amount due, amount paid, and status (Pending, Paid or Overdue).

14.2 Recording a repayment

  1. Enter the Amount received.
  2. Enter the Payment reference from the bank statement.
  3. Click Record.

The payment is applied to the oldest unpaid instalment first, split into principal and interest components, and the outstanding balance reduces. Partial payments are allowed — the instalment stays Pending until fully covered.

Repayments have not been exercised end to end. The repayment path against a bullet schedule was not tested during handover. Record the first live repayment with care and confirm the resulting balance before relying on it. This is item 5 in Section 25.

14.3 Moving a loan through repayment and closure

Advance the case from Disbursed to In Repayment once collection begins, and to Closed when the loan is fully settled. Both are Finance Officer transitions on the left rail.

Repayments are collected by debit order, as the client agrees in their consent declaration. The portal has no payment function by design; the console is where receipts are captured.

15. History, Tasks, Notes and Advisory

15.1 History — the audit trail

History is appended to automatically and cannot be edited. It is what you produce when a decision is queried — which is the argument for writing a real note on every transition.

Alongside status changes, the trail records document decisions and document requests, each against the name of whoever made them:

EntryWritten when
CreateDocumentRequestYou ask the applicant for a document (9.4)
CancelDocumentRequestYou withdraw that request
Status transitionsEvery stage change, with your note

A withdrawn request stays in the trail rather than disappearing, so "we never asked for that" is always checkable.

15.2 Tasks

Tasks track action items against a case. Assigned tasks appear on the assignee's dashboard under Tasks Due Today, and overdue ones generate reminders.

15.3 Notes

Use notes for context that is not a decision — a phone call, a concern, something to watch. Use a status note for the decision itself, so it lands in History.

15.4 Advisory (NFS)

PRDF's mandate includes non-financial support — mentorship, compliance help, training. Logging sessions here is what makes that reportable as development impact rather than an untracked favour.

16. Loans and Portfolio

16.1 Loans

Click a loan reference to open its account. This is the book-wide view; the Money tab is the same loan seen from its case.

16.2 Portfolio

Arrears lists every overdue instalment across the book. An empty arrears panel is the goal; anything in it needs collections attention.

Export CSV downloads the portfolio for reporting or reconciliation outside the system.

Check arrears before month end. Penalties accrue daily with no grace period, so a missed instalment gets more expensive for the client every day it is left. Early contact is cheaper for everyone.

19. My Profile and notifications

Your full name is what colleagues see on assignments, notes and reports, so keep it accurate. Phone is optional. Email is managed by your sign-in and can only be changed by an administrator. Roles are shown for reference.

19.1 Notifications

The bell in the top bar carries a count of unread items. Notifications are raised on status changes, and by scheduled scans for arrears, due tasks and stale cases.

Notifications are in-app only. Nothing is emailed or texted, to staff or to applicants. If a case is waiting on someone, the system will not chase them — the dashboard SLA counter and the arrears panel are your early warning. Adding email delivery is item 3 in Section 25.

20.1 Where their view differs from yours

  • They see six milestones; you see eleven stages. This is not a tidy simplification — six of your statuses map to no milestone at all and blank their whole timeline. The mapping is set out in 21.3 and it is worth knowing before you take a call about it.

  • They cannot edit anything after submitting.
  • They cannot pay through the portal.
Expect this support call. "The tracker says nothing has happened." Their status badge is correct; the circles are not. Reassure them and quote the status label. This is item 1 in Section 25.

21. Your action, their screen

This section pairs the things you do with what the applicant sees when you do them. It exists because two questions come up constantly and neither is answered by looking at the console alone: if I click this, what happens on their side? and they are phoning about something — what are they looking at?

Only screens you cause are shown here. The landing page, the calculator, the eligibility check and the five wizard steps happen before you are involved and live in the Client Portal manual instead.

21.1 You request a document

You raise the request in 9.4. On their side it arrives as a panel at the top of the status card for that application, with an upload box attached to each outstanding item.

Three things are worth knowing when this comes up on a call:

  • They get an in-app notification as well as the panel. It is one of only two notifications the portal sends them — see the table in 21.5.
  • The upload box only accepts the file type you picked. If they say "it won't let me attach it", check what you chose in the File type field before anything else.
  • The panel is not tied to Info Requested. It shows on any status, so an applicant can be asked for a document while their case is still progressing normally.

When they upload, the ask closes itself and the document appears on your Documents tab for verification.

21.2 You verify or reject a document

Your decision in 9.2 and 9.3 shows against that document on their Documents page, as a badge.

Note the Select application picker at the top. An applicant with more than one application sees the documents for whichever is selected, which is not necessarily the case you are discussing — worth confirming at the start of a call.

Neither one notifies them. Verifying and rejecting change the badge silently. An applicant who is not already looking at the page will not know you rejected something — so if a rejection is blocking the case, raise a document request or a Request info alongside it, or telephone them.

21.3 You move the case forward

Your eleven stages do not collapse neatly into their six milestones. Six of your statuses are not in the tracker's vocabulary at all, and when a case is in one of them the applicant's entire timeline goes blank — every milestone grey, including the "Application Submitted" they have already passed. Read the Board Approved and Rejected rows twice. An applicant watching their tracker sees "Approved" light up, and then — when you move the case to Board Approved, which is forward progress — watches it go blank again. A declined applicant is never told they were declined by the timeline at all. Neither is a display quirk you can leave to explain itself on a call: if you decline a case, telephone them, and if you are moving an approved case onward, warn them their tracker will appear to reset.

The cause is mechanical: the tracker orders statuses against a fixed list that never had the review and post-approval stages added to it, so an unlisted status matches no milestone and every circle falls through to "pending". It is item 1 in Section 25 and the highest-value fix in this manual.

21.4 You approve, or decline

Approval renders properly — the Naledi Construction card in the figure above shows Submitted and Under Review ticked with Approved active. It is the step after approval that causes trouble, because moving the case to Board Approved blanks that same timeline (21.3).

Approving also does not release funds and does not create anything they can act on. Between your Approved and their money there is still Board Approved, Contracting and disbursement. Applicants routinely read "Approved" as "paid", so it is worth saying explicitly on the call — and worth warning them that their tracker is about to go blank.

A declined applicant is not told. Rejected is not in the tracker's vocabulary either, so declining a case blanks their timeline exactly as Screening does. There is no "not approved" state on their side and no notification that says it in plain words. Telephone anyone you decline.

22. After approval — the client's loan

Everything to this point has been an application. From disbursement onward the applicant has a loan account, and their portal changes shape. This section follows that from their side, in the order they experience it.

22.1 Approved, but nothing has moved

Covered in 21.4 and repeated here because it generates more calls than anything else: Approved is not funded. Their status reads Approved through your Approved, Board Approved and Contracting stages. My Loans is still empty. There is nothing for them to do and nothing for them to see beyond the milestone.

22.2 You disburse — their loan appears

The moment you record disbursement in 13.1, three things change for them at once: the Disbursed milestone lights up, Home starts showing an outstanding balance, and My Loans stops being empty.

Expect a question about the amount. A client who asked for R500 000 receives less than that in their bank account — the initiation fee and the management fee are deducted from the advance, as Section 12.3 explains — but the balance shown here is what they owe, which is the full principal plus interest. The two numbers are both correct and they will not look it. Section 12.4 has the worked example to read out.

22.3 What they can see about the loan

Opening the loan shows the account and its repayment schedule: what is due, when, and what has been paid.

22.4 The first payment

Repayment is collected by direct debit order, which is what the applicant agreed to in their consent declaration. Collection happens outside the system, and the portal has no payment function — there is no card capture, no way to set up or amend the debit order, and no "pay now" button anywhere in it. The loan only reflects a collection once you record it on the Money tab.

Until you record it, they see nothing. An applicant who paid on Friday and checks on Monday will see an unchanged balance and an instalment still outstanding, and will reasonably conclude the payment was lost. This is the single most avoidable complaint in the system: record receipts promptly, because the portal has no other way of knowing.

22.5 Through repayment to closure

  • In repayment. Each receipt you record reduces the balance and adds a history row. Nothing notifies them.
  • Falling behind. Overdue instalments appear on your Portfolio ageing report (16.2). Penalties accrue daily with no grace period, per Section 12.5. The applicant sees the increased balance but gets no warning before it happens.
  • Settled. When the loan closes, their milestone moves to Closed and the loan stays visible in My Loans as a record.
What the applicant can never do. Pay through the portal, edit a submitted application, change their banking details, upload a document nobody asked for once the application has left Draft, or see your internal notes, tasks, assignments, risk grade or advisory entries. If they need any of those, they need you.

The values PRDF revisits most are configuration, not code. Four of the six below need no developer and no deployment.

23.1 Changing the loan band

Update the amount and term columns on the active product. Sliders, validation and the API all follow within about thirty minutes.

Narrowing a band has a delayed effect. A trigger validates applications against product limits on every write, so an already-submitted case outside a new band fails on its next update, not immediately. After narrowing, check for non-draft cases outside the new limits and re-quote them deliberately.

23.2 Changing pricing

pricing_config holds one row: prime rate, initiation fee, management fee percentage, penalty rate, penalty period and days per year. When Prime moves, update it here — the client-facing disclosure is expressed as a margin over Prime precisely so it stays true.

Existing loans are unaffected. Rate, fees and days financed are snapshotted onto each loan when it is booked, so changing config never re-prices a loan already sold.

23.3 Changing required documents

Add or remove rows in document_requirements. A brand-new document type also needs a label added in code, or the raw type name is displayed.

23.4 Changing consent wording

Edit the consent items and bump the version stamp, so stored consent records stay traceable to what was actually agreed.

The current consent wording is marked draft, pending PRDF legal review. It is captured and versioned correctly, but has not been signed off by legal. Item 2 in Section 25.

  2. Capture the request ID and the failing endpoint.
  3. Confirm row-level-security behaviour in the Supabase SQL editor.
  4. Roll back to the previous deployment if production impact is high.
One production setting to verify. The API's JWT audience setting must be authenticated. During handover it was found holding a secret value instead, which causes every authenticated request to fail with 401 while unauthenticated pages keep working — a confusing failure that looks like a login problem. It has been corrected locally; confirm the production environment matches.

25. Known limitations

Stated plainly so that what is being signed for is clear. None of these stops an application being assessed or funded.
